# Использование AI при разработке

## Моя роль: координатор кодового агента

Я был владельцем задачи и координатором разработки. Я сформулировал план,
бизнес-цель, критерии приёмки и ограничения, выбирал технологии, расставлял
приоритеты для четырёхчасового PoC и принимал итоговые решения. Кодовый агент
был исполнителем: исследовал варианты по моим вопросам, вносил изменения,
запускал проверки и помогал редактировать документацию. Его предложения не
принимались автоматически — я уточнял требования, отклонял лишнее и менял
направление, когда решение не соответствовало цели проекта.

В частности, я задал следующие решения и критерии:

- русский язык данных и интерфейса, четыре входных адаптера и готовые примеры в
  Streamlit;
- FakeLLM для воспроизводимого demo и LiteLLM как единственный путь к реальной
  OpenAI-compatible модели;
- классификатор перед risk gate и точная проверка
  `theme in HIGH_RISK_THEMES`, причём high-risk — только денежные темы;
- три маршрута: безопасный `auto_reply`, черновик `approve_require` и
  `human_need` без LLM;
- hybrid retrieval через Qdrant и локальную embedding-модель, query dataset из
  300 тикетов с ответами и темами, отдельную загрузку документации в KB;
- Redis для типовых повторов, PostgreSQL для audit, обязательный Langfuse для
  trace, RabbitMQ для инцидентных всплесков;
- быстрые автоматические метрики без LLM-as-a-judge и оценку бизнес-эффекта через
  среднюю стоимость ручной обработки тикета.

## Где помогал кодовый агент

AI использовался для поиска и сравнения открытых подходов, декомпозиции
архитектуры, реализации согласованного PoC, тестов, benchmark и документации, а
также для поиска edge cases. Я проверял результат по условию задания, локальным
тестам и метрикам и оставлял за собой финальный выбор компромиссов.

Предложения AI, которые были отклонены или упрощены:

- Kubernetes, Kafka и полный MLOps-стек не нужны для четырёхчасового PoC;
- первоначальный LightRAG конфликтовал с требованием не использовать LLM при
  построении KB, поэтому заменён на Qdrant + embeddings;
- BGE-M3 оказался слишком тяжёлым для компактного CPU-запуска, поэтому выбран
  RuBERT Tiny 2, а качество оставлено на проверку live benchmark;
- LLM-классификация заменена быстрым TF-IDF baseline;
- query dataset не индексируется в Qdrant, чтобы не было утечки оценки.

Примеры ошибок и исправлений после проверки:

- первый benchmark обнаружил high-risk false negative; добавлен ограниченный
  safety re-ranking только среди Top-3 классификатора;
- двух маршрутов оказалось недостаточно для безопасных нестандартных вопросов;
  добавлен операторский черновик `approve_require`;
- пустой Qdrant API key ломал авторизацию; проблему обнаружил smoke-запуск и
  конфигурация была сделана явной;
- Redis не решает очередь при инцидентном burst; после повторной проверки
  архитектуры добавлен отдельный минимальный RabbitMQ-контур с backpressure и DLQ.

Итоговые classifier-числа взяты из локального benchmark. Непроверенные метрики
не выдаются за полученные. AI ускорил исполнение, но постановка задачи,
координация агента, границы автоматизации, risk policy, выбор стека и принятые
компромиссы остались моей ответственностью.
